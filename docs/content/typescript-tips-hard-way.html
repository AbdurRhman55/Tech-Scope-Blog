Most TypeScript pain comes from fighting the compiler instead of letting it change how you model data. The tips below are the ones newcomers learn the hard way — each with a before/after pair, the failure it prevents, and the setting that turns it on.

The direct answer: enable strict mode on day one, model states as a discriminated union instead of a pile of booleans, treat every index and every network response as undefined or unknown until proven otherwise, and stop silencing the compiler with any, ! and as. The goal is not fewer types — it is fewer production incidents. The samples here are illustrative snippets written to show compiler behavior, not transcripts of a run.

Turn on strict mode first

strictNullChecks alone eliminates a whole class of runtime surprises. Endure a couple of days of red squiggles: that is the compiler showing you where your code already assumed a value existed.

Before — permissive defaults, where "maybe missing" is silently the same as "present":

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler"
  }
}

After — the settings that pay for themselves in the first week:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true
  }
}

Under strict, optional properties become visible to the compiler:

Before — compiles without complaint, fails at runtime on the first user without a name:

function displayName(user: { name?: string }): string {
  return user.name.toUpperCase();
}

After — the missing value is handled in the type, at the point of use:

function displayName(user: { name?: string }): string {
  return (user.name ?? "Anonymous").toUpperCase();
}
  • strict bundles the important flags, including strictNullChecks and noImplicitAny.
  • noUncheckedIndexedAccess adds undefined to every index signature — the single most under-rated option in the compiler.
  • Migrating a legacy codebase? Turn on strictNullChecks first, module by module, rather than flipping every flag at once and stalling the team.
  • Write new code with the flags already on; a codebase that grows without strict accumulates assumptions that get expensive to unwind.

Model state with discriminated unions

A request is loading, success or error — never all three. Discriminated unions make the compiler enforce your state machine, instead of letting impossible combinations compile.

Before — four independent fields, and every combination of them is legal to the type system, including the ones that make no sense:

interface RequestState {
  isLoading: boolean;
  isError: boolean;
  data: Post[] | null;
  errorMessage: string | null;
}
// isLoading: true, isError: true, data: [Post], errorMessage: "boom"
// nothing stops a caller from building this

After — one field decides which shape the value has:

type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; posts: Post[] }
  | { status: "error"; message: string };

function banner(state: RequestState): string {
  switch (state.status) {
    case "idle":
      return "Nothing loaded yet";
    case "loading":
      return "Loading\u2026";
    case "success":
      return `${state.posts.length} posts`;
    case "error":
      return state.message;
  }
}

Inside each case, TypeScript knows exactly which fields exist: state.posts is legal only where it is real, and state.message only where it is guaranteed. Add a fifth status and every switch that must handle all of them fails to compile until you deal with it.

  • Give every union a literal discriminant — status, kind, type — never a boolean you have to correlate by hand.
  • Put the data each state needs inside that variant; shared fields are still fine, extra fields are not.
  • Pair the union with an exhaustiveness check (never) if you prefer the compiler to force a default branch.
  • This same shape models domain events, form states and WebSocket messages — anywhere a value is "one of these, and the others are invalid".

Array footguns

Arrays are where false confidence hides: indexing never fails at the type level unless you ask it to, and empty arrays are perfectly legal in types that promise elements.

Before — typed as a number it does not have to be:

function firstOrderTotal(orders: Order[]): number {
  return orders[0].amount; // no compile error; throws on an empty array
}

After — two honest versions, depending on what empty means in your domain:

// empty is a legitimate answer
function firstOrderTotal(orders: Order[]): number | undefined {
  return orders[0]?.amount;
}

// empty is a programming error
function requireFirstOrderTotal(orders: Order[]): number {
  const first = orders[0];
  if (first === undefined) {
    throw new Error("orders must not be empty");
  }
  return first.amount;
}
  • Array.at(-1) returns T | undefined — always, because the index may be past the end. Handle it with ?? or a guard, not with !.
  • Never index with noUncheckedIndexedAccess off in real projects; that option is what makes orders[0] read as Order | undefined.
  • find() also returns T | undefined. So does pop(), and so do lookups into records: indexing a Record<string, T> yields T | undefined under the same flag.
  • filter(Boolean) does not narrow an array to non-empty values — the result is still typed as the same element type, and the compiler will not tell you the list is non-empty.
  • If a function must never receive an empty list, say so in the parameter type ([Order, ...Order[]]) or check at runtime and throw.

Details of the method itself are documented on MDN's Array.at() reference.

Treat outside data as unknown

Everything from outside your program — request bodies, localStorage, third-party APIs, JSON.parse — arrives without types. TypeScript's types are erased at build time, so nothing validates a network response just because you annotated it.

Before — a cast that silences the compiler instead of checking the data:

const config = JSON.parse(raw) as Config;
config.theme.darkMode = true; // compiles; throws if the stored shape is different

After — parse into unknown, validate the shape, then let narrowing do the rest:

type Config = { theme: "light" | "dark"; retries: number };

function parseConfig(raw: string): Config {
  const value: unknown = JSON.parse(raw);

  if (typeof value !== "object" || value === null) {
    throw new Error("config must be an object");
  }

  const { theme, retries } = value as { theme?: unknown; retries?: unknown };

  if (theme !== "light" && theme !== "dark") {
    throw new Error("theme must be light or dark");
  }
  if (typeof retries !== "number") {
    throw new Error("retries must be a number");
  }

  return { theme, retries };
}
  • any disables the compiler for that value and everything it touches; unknown forces you to prove the shape before use.
  • One cast of unknown to a structural shape, immediately followed by validation, is legitimate. A cast that jumps straight to your domain type is a comment, not a check.
  • Validate once, at the boundary, and pass the typed value inward — internal code should never need to re-check the same field.
  • The same rule covers HTML forms, query strings and message queues. Annotating the variable does not make the bytes conform.

Retire the non-null assertion

The ! operator says "trust me" to the compiler and erases the exact warning you will need later. It converts a possible runtime crash into a silent one.

Before — both assertions compile, and neither is checked:

// users: User[] where User = { id: string; profile: { bio: string } }
function showProfile(id: string): string {
  const user = users.find((u) => u.id === id)!;
  return user.profile.bio;
}

After — the miss becomes a branch you can test and reason about:

function showProfile(id: string): string {
  const user = users.find((u) => u.id === id);

  if (!user) {
    throw new Error(`no user with id ${id}`);
  }

  return user.profile.bio;
}
  • Throw, return a default, or narrow — but make the missing-value path visible in the code.
  • If a function returns T | undefined and you assert at every call site, the union was the wrong return type: fix it at the source.
  • Code review heuristic: every ! is a question someone decided not to answer.

Narrow instead of casting

as replaces the compiler's knowledge with your assertion. A type guard replaces it with a check the compiler can verify.

Before — the classic DOM workaround, which lies whenever the event came from somewhere else:

function onInput(event: Event): void {
  const input = event.target as HTMLInputElement;
  input.value = ""; // compiles even if target is not an input
}

After — instanceof narrows the type and eliminates null at the same time:

function onInput(event: Event): void {
  if (!(event.currentTarget instanceof HTMLInputElement)) {
    return;
  }

  event.currentTarget.value = ""; // typed as HTMLInputElement, checked at runtime
}
  • Prefer typeof, instanceof, "key" in value, or a literal comparison on a discriminant over as.
  • Use satisfies when you want to check a value against a type without changing its inferred, more specific type.
  • Assertions belong at trust boundaries you have already validated — not in the middle of business logic.

Freeze constants with as const and readonly

const only protects the binding. The object or array it points at is still mutable, which is why "constants" get quietly rewritten three files away.

Before — declared once, changed anywhere:

const config = { retries: 3, regions: ["eu", "us"] };
config.retries = 99; // no error: only the binding was constant
const list: string[] = ["a"];
list.push("z"); // also fine

After — literal types captured, mutation rejected:

const config = { retries: 3, regions: ["eu", "us"] } as const;
config.retries = 99; // error: Cannot assign to 'retries' — read-only

type Status = "idle" | "loading" | "done";
const queue: readonly Status[] = ["idle"];
queue.push("done"); // error: push does not exist on readonly arrays

function print(config: Readonly<Config>): void {
  // ...
}
  • as const on a literal also gives you literal types — handy for maps keyed by a fixed set of strings.
  • readonly on parameters and properties documents intent that callers can rely on.
  • Freezing is shallow: nested objects still need readonly in their own type, or Object.freeze() at runtime if you truly need enforcement.

Write types at the boundaries, infer everywhere else

Explicit annotations matter most where code meets the outside world or where other teams import your work. Inside a function, inference is usually better: it follows from the expression, so it cannot drift.

Before — annotations that add noise and can lie after a refactor:

const userName: string = "ada";           // inference already knew
let count: number = 0;                    // same
function items(): Order[] {
  return load().map((row) => row as Order); // asserting instead of parsing
}

After — annotate what others depend on, infer the rest:

function clampPercent(value: number): number {
  const rounded = Math.round(value);
  return Math.min(Math.max(rounded, 0), 100);
}

export function formatDiscount(value: number): string {  // return type written down
  return `${clampPercent(value)}% off`;
}
  • Annotate exported function signatures: a public return type should not change because an internal helper changed.
  • Annotate function parameters — otherwise noImplicitAny errors in strict mode anyway.
  • Leave local variables to inference; the compiler reads the initializer you just wrote.
  • Reach for generics only when you have at least two concrete uses; a premature generic is a type system you must now maintain.

When types get in your way

Honest limits, so strict mode does not turn into a fight:

  • Types are erased at runtime. A perfect Config annotation cannot make a malformed server response valid — validate at the boundary or the type is fiction.
  • Whole-project flags, incremental adoption. strict is a compiler-wide switch; on a large legacy codebase, enable pieces (often strictNullChecks first) and fix by module instead of freezing feature work.
  • Deeply dynamic data resists precise types. Parsers and schema-validation libraries exist for this reason; hand-rolling exhaustiveness for recursive JSON is usually the wrong trade.
  • Over-annotation slows you down. If you are typing what inference already knows, you are writing maintenance, not safety.
  • Generics used too early become a maze. Start concrete; abstract when the second use case arrives.
  • Type-level cleverness has a reader cost. A slightly looser type with a clear name beats a conditional type nobody on the team can explain.

Key takeaways

  • Turn on strict (and noUncheckedIndexedAccess) before the codebase accumulates assumptions you have to unwind.
  • Model "one of several states" as a discriminated union so impossible combinations stop compiling.
  • Indexing, .at(), find() and pop() all yield possibly-missing values; handle them with narrowing, not assertions.
  • Data from outside is unknown until validated — a cast is not a check.
  • Replace ! and as with guards, and const object literals with as const / readonly.
  • Annotate the boundaries other people depend on; let inference handle the middle.

The goal is not fewer types — it is fewer production incidents. Start with one change today: add "strict": true to your tsconfig.json and read what the compiler points at. Then keep the habit going on the rest of the codebase with the discipline described in clean code patterns for PHP, and make sure each of these fixes lands as a small, reviewable change under the short-branch workflow.
