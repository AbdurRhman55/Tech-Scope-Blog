Teams reach for fine-tuning when they should be retrieving, and vice versa. The choice is less about hype and more about where your knowledge lives and what you are actually trying to change: facts, or behaviour. This article gives you a criteria-based way to decide, a decision framework you can run in ten minutes, a worked (hypothetical) example of each path, and the combinations that cover the cases neither option solves alone.

The short answer

Use retrieval-augmented generation (RAG) when the model needs knowledge — your documents, tickets, policies, product data — that changes over time, must be cited, or must never leak into a shared artifact. Use fine-tuning when the problem is behaviour: the model already knows enough, but you want a consistent tone, output format, domain vocabulary, or task pattern that prompting keeps failing to enforce. If neither of those sentences describes your problem, prompting with good context is probably enough, and both options are premature.

Keep one sentence in mind throughout: retrieval changes what the model reads; fine-tuning changes how the model writes. Almost every argument between the two is really an argument about which of those you lack.

What RAG actually does

RAG keeps knowledge outside the model, in a searchable index, and injects the relevant pieces into the context at request time. The mechanics:

  • Ingestion: documents are split into chunks, each chunk is turned into an embedding vector, and stored in a vector index (often alongside full-text search — many production systems combine both).
  • Retrieval: the incoming question is embedded with the same model, and the index returns the most similar chunks, optionally reranked by a stronger model.
  • Assembly: the retrieved chunks are placed into the prompt together with the task instructions and constraints — the job described in context engineering.
  • Generation: the frozen base model answers from that context, ideally pointing to which chunk supports each claim.

What this buys you:

  • Freshness without retraining. Updating a fact is an index update — minutes of work, not a training run.
  • Citations and auditability. Because every answer is grounded in retrieved chunks, you can show the reader the source passage.
  • One base model, many knowledge domains. Swap or re-rank indexes without touching weights; a single deployment can serve several document sets.
  • Access control at query time. Retrieval can filter chunks by user permissions, so two users can hit the same model and see different evidence. Fine-tuning cannot do this — trained weights leak to everyone who can query the model.

What it does not buy you: RAG does not reliably change tone, it cannot teach a new output format, and every retrieval miss becomes a generation miss. Its failure mode is quiet — plausible answers built on the wrong chunk.

What fine-tuning actually does

Fine-tuning continues training on a curated set of examples so the model's weights shift toward the behaviour you demonstrated. In practice teams use parameter-efficient methods (adapters such as LoRA-style fine-tunes) that train a small set of additional weights and keep the base model frozen, which makes runs cheaper and variants swappable. What it can and cannot change:

  • It changes behaviour: tone, formatting, refusal style, domain vocabulary, the shape of a structured output, recurring task patterns like classification or extraction.
  • It bakes in style, not up-to-date facts. Stuffing facts into training data is a poor knowledge store: the model learns them unreliably, cannot cite them, and you have no way to delete one fact without retraining.
  • It needs examples, not documents. The unit of fine-tuning data is a worked input/output pair at the quality you want. Curating a few hundred to a few thousand consistent examples is usually the hardest part of the project.
  • It creates a maintenance artifact. Every base-model update means retraining; every behaviour change means a new dataset version and an evaluation run.

The clearest signal that fine-tuning is the right tool: your prompt is already correct, your context already contains the right information, and the model still answers in the wrong style or format. If the information is missing instead, fine-tuning will only teach it to produce wrong answers more confidently.

There are no numbers in that table on purpose. Latency, cost and quality differences between the options vary enormously with model size, hardware, index size and workload shape, so any universal figure would be misleading; instead, reason about the structure of each cost and measure your own system.

Walking the criteria

Freshness and citability

Ask one question: does the answer depend on something that could change after you build the feature? If yes, retrieval is not optional — fine-tuned weights cannot be patched. A pricing policy, an on-call schedule, a product catalog: all retrieval. A house style guide, an output schema, the general shape of a good SQL review: all candidates for fine-tuning, because they change on a timescale of months.

Latency

RAG adds a retrieval (and often a reranking) step before generation — work that runs serially after the user's request arrives. Fine-tuning adds nothing at query time. If your budget for a whole response is tight, retrieval quality choices (smaller index, single-stage retrieval, cached answers for frequent questions) matter more than model choice.

Cost structure

RAG spends money continuously: index storage, embedding calls for ingestion, retrieval compute, and the larger prompts that retrieved chunks produce. Fine-tuning spends money up front — dataset curation (the expensive part), training runs, evaluation — and little after, until the base model or the desired behaviour changes. Neither is categorically cheaper; they fail at different budget lines.

Security and compliance

This criterion alone decides projects. If per-user document permissions matter, RAG with query-time filtering is effectively the only option of the two: fine-tuning merges all training data into shared weights. If your deployment is fully offline for privacy reasons, the question moves upstream — including the weights may push you toward running an open-weight model locally, which is exactly what the local LLM guide covers.

A decision framework

Run these questions in order; the first "yes" usually settles it.

  1. Do the answers depend on facts that change, or on private data? Yes → RAG. Stop here unless the second problem also exists.
  2. Does the behaviour itself need to change — tone, format, task pattern? Yes → fine-tuning, with a plan for examples and evaluation.
  3. Is the prompt just… not good yet? Then you are early in the process, not at a crossroads: fix the context and instructions first, and revisit this framework once prompting plateaus. The default ordering is still the original one — start with retrieval plus strong prompting, fine-tune only after prompt fatigue is measurable, and budget for evaluation either way, because you cannot improve what you do not measure.

A worked example (hypothetical)

Imagine a support assistant for a B2B invoicing product. Both techniques apply to it — at different layers — which makes it a useful illustration.

  • The knowledge problem: answers must reflect current plan limits, this quarter's pricing, and the changelog. These change constantly and must be citable when a customer disputes a charge. → RAG over the help center, pricing page and changelog, with permissions filtered per account tier.
  • The behaviour problem: default model answers are too chatty, open with apologies, and bury the fix below three paragraphs of preamble. Repeated prompt instructions reduce this but never eliminate it. → Fine-tune on a few hundred curated conversations showing the tone you want: lead with the fix, one sentence of empathy, then the steps.
  • The layer underneath both: neither works without a small evaluation set — say, a set of real (anonymised) customer questions with the answers your best human would accept, run before every change to retrieval, prompt, or model. This is the artifact that turns "we think it improved" into a number your team can point at.

Note the order of work: prompts and retrieval first, fine-tuning last. In most teams the fine-tuning step turns out to be unnecessary once retrieval quality and context assembly are fixed — which is exactly why the framework puts it behind two gates.

Combinations and middle options

The dichotomy is useful but not exhaustive. Between "just prompt" and "train weights" there is a gradient:

  • Prompting + context engineering alone. Cheapest to try, fastest to change, and the correct first move for most tasks.
  • RAG with reranking and query rewriting. A quality upgrade inside the retrieval path — better chunks in the context without touching the model.
  • RAG + fine-tuning together. Legitimate and common at scale: retrieval supplies the facts, fine-tuning supplies the format and tone. If you do this, evaluate each part separately or you will never know which change helped.
  • Tool use / function calling. When the "knowledge" is actually live system state — an order status, a database row — a tool call is more honest than a document retrieval, and avoids pretending a snapshot is knowledge.

Common mistakes

  • Fine-tuning to inject facts. The most expensive mistake in this space: slow, unciteable, undeletable, and unreliable for recall.
  • Building RAG for a style problem. If the retrieved text is already in the prompt and the output format is still wrong, no amount of retrieval tuning will fix the format.
  • No evaluation set before either project. Without one, both projects become vibes: you cannot tell regression from improvement.
  • Chunking by page count instead of by meaning. Retrieval quality is decided at ingestion; chunks that split an answer from its context produce confident, wrong generations.
  • Skipping the prompt-fatigue measurement. Teams often fine-tune because prompting felt frustrating, not because it was measured to be failing.
  • Assuming the newest base model needs the same treatment. Model behaviour shifts release to release; both decisions are version-sensitive, so re-check them (as of October 2026) whenever you change base models.

Key takeaways

  • Retrieval changes what the model reads; fine-tuning changes how the model writes. Identify which one you lack before choosing a tool.
  • Fresh, private or citable knowledge → RAG. Stable behaviour, format or vocabulary → fine-tuning. Neither → fix your prompting first.
  • Cost and latency differences are structural, not absolute: RAG is a recurring spend plus a per-request step; fine-tuning is an upfront spend plus a maintenance burden.
  • Permissions-sensitive data makes RAG with query-time filtering effectively mandatory; fine-tuned weights are shared with everyone who can query the model.
  • The two techniques compose: the common production pattern is retrieval for facts, fine-tuning for format, evaluation for both.
  • No evaluation set, no decision — build a small graded test set from real questions before you choose anything.
