Clean code is not about cleverness; it is about the next developer — who is usually you, six months from now, with no memory of this. This article collects the PHP habits that keep a codebase maintainable when the deadline has passed and someone has to add one more feature without breaking three others.

The direct answer: a maintainable PHP codebase is the product of four small disciplines — name things after intent, keep every function to one job, never trust input, and cover behaviour with tests that survive refactoring. Patterns help, but they are tools for those disciplines, not a substitute for them. What follows is a before/after for each discipline, the security baseline every PHP application needs, a testing habit that pays for itself, and an honest list of when these habits are not worth applying.

Name things after intent

$data tells you nothing. $publishedPosts tells you everything. Names are documentation that cannot go stale, because the compiler enforces them: rename a variable and every use of it changes with it, while a comment quietly keeps describing yesterday's design.

Before — the reader has to open three files to learn what $data holds and what st means:

$data = getStuff($id);
if ($data['st'] == 1) {
    echo $data['t'];
}

After — the domain concept is in the name, and the branch reads like a sentence:

$post = $posts->find($id);
if ($post->isPublished()) {
    echo $post->title();
}
  • Name functions after what they return or do, not how they do it: paidOrders(), not loopAndFilter().
  • Name booleans so they read as questions: isPublished(), hasValidLicense().
  • Eliminate abbreviation: $cnt, $mgr, $tmp cost more characters to decode than they save to type.
  • One concept, one name. If the same thing is $user, $account and $actor across files, pick one and use it everywhere.
  • Delete $data2, $resultOld, $newFlag2. If something needs a suffix, it is a different thing — or dead code.

Small functions, single jobs

If a function needs a comment to explain its steps, split it. Each function should do one thing and do it well — and "one thing" means one reason to change, not one line of code.

Before — filtering, sorting, formatting and output are four different reasons to change, welded into one body:

function summaryReport(array $orders): void
{
    $paid = array_filter($orders, fn (array $o) => $o['status'] === 'paid');
    usort($paid, fn (array $a, array $b) => $b['total'] <=> $a['total']);

    foreach ($paid as $order) {
        echo $order['customer'] . ': ' . $order['total'] . PHP_EOL;
    }
}

After — each step is named, testable on its own, and reusable by the next report:

function paidOrders(array $orders): array
{
    return array_values(array_filter($orders, fn (array $o) => $o['status'] === 'paid'));
}

function byTotalDescending(array $orders): array
{
    usort($orders, fn (array $a, array $b) => $b['total'] <=> $a['total']);
    return $orders;
}

function summaryLine(array $order): string
{
    return $order['customer'] . ': ' . $order['total'];
}
  • A useful size test: you can say what the function does in one sentence without using "and then".
  • Parameters should be inputs the function cannot derive itself. Four or more of them usually means a small value object is missing.
  • Pure functions — in, compute, return — are trivial to test. Push printing, database writes and clock reads to the edges.
  • Small does not mean one-liners everywhere. A 15-line function with one job is better than five lines that each need a paragraph of context.

Guard clauses instead of nested conditionals

Deep nesting hides the error. Reviewers skim, and the branch they skim is the one that ships the bug. Return early for the unhappy paths, and leave the happy path flat at the top level of the function.

Before — the important line sits three levels deep, and the indentation has to be tracked mentally:

function approveInvoice(Invoice $invoice, User $user): void
{
    if ($user->isActive()) {
        if ($invoice->isWithinBudget()) {
            if ($invoice->isApproved() === false) {
                $invoice->approve();
            }
        }
    }
}

After — each refusal is stated once, and the action stands alone:

function approveInvoice(Invoice $invoice, User $user): void
{
    if (!$user->isActive()) {
        return;
    }
    if ($invoice->isWithinBudget() === false) {
        return;
    }
    if ($invoice->isApproved()) {
        return;
    }

    $invoice->approve();
}

The behaviour is identical; the reading cost is not. When you later add a fourth condition — "the invoice is not older than 30 days" — you append another three-line guard instead of another nesting level.

Make invalid states hard to represent

Most runtime surprises in PHP come from values that were never validated at the boundary: a string where an int was promised, a percentage of 150, a date that is "null but maybe empty". Modern PHP gives you cheap ways to make illegal states unrepresentable — type declarations, constructor guards and enums.

final class Discount
{
    public function __construct(
        private string $code,
        private int $percent,
    ) {
        if ($percent < 0 || $percent > 100) {
            throw new \InvalidArgumentException('percent must be between 0 and 100');
        }
    }

    public function apply(float $amount): float
    {
        return round($amount * (100 - $this->percent) / 100, 2);
    }
}
  • Declare parameter and return types on every function you write; the engine then rejects wrong values at the call site instead of deep inside.
  • Validate in the constructor, once, where the object is born — not in every method that happens to read the field.
  • Use enum (PHP 8.1+) for closed sets such as order status instead of a free-form string that accepts 'shippedd'.
  • Prefer throwing over returning null for "this should never fail" invariants; prefer returning over throwing for expected, caller-handled outcomes.
  • Do the opposite for external data: arrays from JSON, $_GET and database rows arrive untyped, so convert them into typed objects at the edge.

Security baseline: never trust input

Use PDO prepared statements for queries, escape output with htmlspecialchars(), and validate on the server — always. Client-side validation is a courtesy to the user, never a control. Two lines of discipline here prevent the two most common PHP vulnerabilities: injection and cross-site scripting.

$stmt = $pdo->prepare("SELECT * FROM posts WHERE slug = ?");
$stmt->execute([$slug]);

Before — the request array is concatenated straight into SQL and printed straight into HTML:

$sql = "SELECT * FROM posts WHERE slug = '" . $_GET['slug'] . "'";
$rows = $pdo->query($sql)->fetchAll();

echo '<h1>' . $_GET['title'] . '</h1>';

After — the query is parameterized, the value is checked against an allowlist, and output is escaped for its context:

$slug = $_GET['slug'] ?? '';
if (preg_match('/^[a-z0-9-]{1,80}$/', $slug) !== 1) {
    http_response_code(422);
    exit;
}

$stmt = $pdo->prepare('SELECT title, body FROM posts WHERE slug = :slug');
$stmt->execute(['slug' => $slug]);
$post = $stmt->fetch();

if ($post === false) {
    http_response_code(404);
    exit;
}

echo '<h1>' . htmlspecialchars($post['title'], ENT_QUOTES, 'UTF-8') . '</h1>';

Notice the column list in the "after" query: SELECT * is a habit worth dropping on its own — fetching columns you never read costs memory and hides schema changes from the reader. For the other side of the query — how statements and indexes interact once they are parameterized — our practical guide to SQL indexing takes it from there.

  • Parameterize every query. No string building, no sprintf() into SQL, no exceptions for "internal only" parameters.
  • Escape at the point of output, not the point of input. htmlspecialchars($value, ENT_QUOTES, 'UTF-8') for HTML body text and attributes; JSON-encode for JavaScript contexts.
  • Validate with allowlists, not blocklists. "Only these characters may appear" survives everything you forgot to forbid.
  • Hash passwords with password_hash() and verify with password_verify(); never roll your own, never store a plain or reversibly encrypted password.
  • Check authorization server-side on every request. Being logged in is authentication; being allowed to edit this record is authorization, and it is checked per resource.
  • Keep secrets out of the repository. Configuration comes from the environment; a credential committed once is compromised forever.

Test the behaviour, not the implementation

Tests that break when you refactor without changing behaviour are slowing you down, not protecting you. A test should assert what a caller can observe — returned values, resulting state, output — and stay silent about which private methods were called on the way.

use PHPUnit\Framework\TestCase;

final class DiscountTest extends TestCase
{
    public function testApplyReducesTheAmountByTheConfiguredPercent(): void
    {
        $discount = new Discount('WELCOME20', 20);

        $this->assertSame(80.0, $discount->apply(100.0));
    }

    public function testPercentOutOfRangeIsRejectedAtConstruction(): void
    {
        $this->expectException(\InvalidArgumentException::class);

        new Discount('BROKEN', 150);
    }
}
  • Name tests after the behaviour: testExpiredCouponIsRejected documents a rule; testSetters documents nothing.
  • Assert on outputs and state, never on call counts of collaborators you just extracted.
  • One behaviour per test. When a test fails, the test name should tell you which rule broke.
  • Test the boundary values — 0, 1, an empty string, a missing key — where PHP's loose comparisons used to hide surprises.
  • Keep the suite fast enough that running it is cheaper than thinking about whether to run it.
  • Write the test for the bug you just fixed, first, so the fix can never silently regress.

This habit connects to how your team works, not just to your code: a test suite only pays off if it runs on every change, which is part of the branch and review workflow rather than an afterthought.

Common smells and their first fix

You will not rewrite the codebase, and you should not try. Most maintainability gains come from recognizing a small set of recurring smells and fixing them the moment you touch the file.

$data, $arr1, $tmpReader must open another file to learn what it holdsRename to the domain concept: $publishedPosts
One function that filters, sorts, formats and printsEvery change risks breaking the other three jobsSplit into one function per step, keep a thin caller

Commented-out code blocksHistory belongs in version control, not in the fileDelete it; the diff is one git log away

A worked refactoring: one handler, before and after

Here is a realistic endpoint — a rough search over orders — rewritten with the habits above. Nothing architectural changes: same file, same framework-agnostic PHP, same result for the caller.

Before — one function, unvalidated input, concatenated SQL, no types, output mixed with logic:

function h()
{
    $q = $_GET['q'] ?? '';
    $pdo = $GLOBALS['pdo'];
    $rows = $pdo->query("SELECT * FROM orders WHERE email LIKE '%" . $q . "%'")
        ->fetchAll();

    $out = '';
    foreach ($rows as $row) {
        if ($row['status'] != 'shipped') {
            if ($row['total'] > 0) {
                $out .= $row['email'] . ',' . $row['total'] . "\n";
            }
        }
    }
    echo $out;
}

After — validation at the edge, a prepared statement, one job per function, and a handler that only orchestrates:

function matchingOrders(PDO $pdo, string $emailFragment): array
{
    $stmt = $pdo->prepare(
        'SELECT email, total
           FROM orders
          WHERE email LIKE :fragment
            AND status <> :status
            AND total > 0'
    );
    $stmt->execute([
        'fragment' => '%' . $emailFragment . '%',
        'status'   => 'shipped',
    ]);

    return $stmt->fetchAll(PDO::FETCH_ASSOC);
}

// In the request handler:
$fragment = trim($_GET['q'] ?? '');
if (preg_match('/^[A-Za-z0-9@. -]{0,64}$/', $fragment) !== 1) {
    http_response_code(422);
    exit;
}

header('Content-Type: application/json');
echo json_encode(matchingOrders($pdo, $fragment), JSON_THROW_ON_ERROR);

What improved, concretely: the injection surface is gone because the value is bound, not interpolated; the filter rules live in one query instead of scattered if branches; matchingOrders() can be unit-tested with a fixture database or a stubbed PDO; and the response format is now explicit. What did not change: no interface was extracted, no container was introduced, and no design pattern was named in the diff.

When these habits backfire

Clean-code advice fails when it is applied as ritual instead of judgment. The honest boundaries:

  • One-off scripts. A 100-line migration or report script needs clarity, not repositories, interfaces and dependency injection. Structure is an investment; only make it where code will keep living.
  • Premature abstraction. Three similar functions are cheaper than one wrong base class. Wait until the duplication has repeated, then extract what is genuinely shared.
  • Framework-fighting. In Laravel or Symfony, the framework's conventions are the maintainability. Inventing your own service layer beside it produces two systems to learn.
  • Micro-optimizing clear code. Profile before trading readability for speed. Correctness first, then measured performance, then elegance.
  • Name inflation. AbstractPostRepositoryGatewayFactory is precise and useless. Intent beats ceremony.
  • Test-dosage. Testing every private branch of a leaf utility burns hours without catching real regressions. Test the behaviours that would hurt if they broke.

There is also a social limit: none of this survives a team that does not review it. Naming and splitting are conventions, and conventions hold when pull requests are small and reviewers can actually read them.

Key takeaways

  • Maintainability comes from four disciplines — intent-revealing names, single-job functions, guarded input, and behaviour tests — not from a folder structure.
  • Before/after beats theory: rename, split, guard-clause and parameterize the file you are already touching, and the codebase improves without a rewrite.
  • Security is part of clean code: prepared statements, context-aware output escaping, allowlist validation, server-side authorization and password_hash().
  • Tests protect behaviour; tests that pin implementation actively resist refactoring and should be rewritten.
  • Patterns are earned. Add structure when change pressure proves you need it, not before.
  • The habits are cheap individually and compounding collectively — but only if the team reviews them.

Maintainable code is a series of small, boring, disciplined decisions. That is the whole secret. Pick one habit from this article and apply it to the next file you open — rename something, split something, add one test — and keep going.
