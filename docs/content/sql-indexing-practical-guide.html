Most “slow database” horror stories end the same way: a missing index. The fix is rarely mysterious — but the reasoning behind it often is, and that is where teams lose days. This guide explains what an index physically is, how the engine walks one, how to choose composite-index column order, and how to prove with EXPLAIN that your change actually helped. When an index lets the engine skip a full table scan, the speedup is usually measured in orders of magnitude — but only when the index matches the query, and indexes are never free.

The direct answer: what an index buys you

An index is a separate, sorted structure maintained on one or more columns that lets the storage engine locate matching rows by reading a handful of pages instead of every page in the table. In MySQL with InnoDB, a query that can use a suitable index performs an index scan; a query that cannot performs a full table scan and examines every row, discarding almost all of them.

  • Reads: a filtered query drops from touching the whole table to touching only the matching index entries.
  • Sorting: an index in the right order can satisfy ORDER BY without a separate sort pass (no Using filesort in the plan).
  • Joins: the inner side of a join looks up the outer side's value instead of rescanning.
  • Uniqueness: a unique index enforces a rule the database guarantees for you, faster than a SELECT-then-INSERT check.
  • Cost: every index is extra work on INSERT, UPDATE and DELETE, extra disk, and extra memory in the buffer pool.

If you remember one sentence from this article: index the columns the engine must filter and sort on, then verify the plan with EXPLAIN instead of trusting intuition.

How a B-tree search works

MySQL's default index structure is a B-tree — more precisely a B+tree: a balanced tree of pages where every leaf page sits at the same depth. Three properties explain almost all of the speedup:

  • Balanced: inserts and deletes keep all leaves at the same depth, so a lookup costs the same for a million rows as for a thousand. Depth grows logarithmically, not linearly — the classic O(log n) versus O(n) difference between an index lookup and a full scan.
  • Fan-out: each page holds many keys, so a table with millions of rows is typically resolved in only a few page reads, not thousands.
  • Sorted leaves: leaf pages store entries in key order and are linked together, which is what makes range scans (BETWEEN, >=, ORDER BY) cheap: find the start, then walk the chain.

Two details that matter in practice:

  • InnoDB's secondary indexes store the primary key value in the leaf, not a pointer to the row. That means a secondary-index lookup effectively performs two steps: read the index, then read the clustered index (the table itself, organized as a B+tree on the primary key) to fetch columns that are not in the index.
  • An index that already contains every column the query needs is called a covering index. The engine can answer straight from the index leaf and skips the second step entirely — the Extra column in the plan then says Using index.

A worked example, end to end

Consider a typical blog-style table. The schema below is illustrative but realistic:

CREATE TABLE posts (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  author_id    BIGINT UNSIGNED NOT NULL,
  status       VARCHAR(20)     NOT NULL,
  published_at DATETIME        NOT NULL,
  title        VARCHAR(180)    NOT NULL,
  body         MEDIUMTEXT      NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- An editorial query that runs on the home page
SELECT id, title
FROM posts
WHERE status = 'published'
  AND published_at >= '2026-09-01'
ORDER BY published_at DESC
LIMIT 20;

With no index beyond the primary key, the engine has one option: read every row of posts, throw away anything that is not published and recent, sort the survivors, and return twenty of them. Now add an index whose column order mirrors the query:

CREATE INDEX idx_posts_status_published_at
  ON posts (status, published_at);

Before: full table scan

Run EXPLAIN before the change. The output below is example output — a realistic but illustrative plan; the row counts are optimizer estimates and will differ on your data:

-- Example output (simplified to the columns that matter), before the index
table | type | possible_keys | key  | key_len | rows  | Extra
posts | ALL  | NULL          | NULL | NULL    | 48210 | Using where; Using filesort

Read that line: type = ALL means a full scan, key = NULL means no index was usable, and Using filesort means the sort could not come from an index, so every matching row had to be buffered and sorted.

After: index range scan

-- Example output (simplified), after CREATE INDEX
table | type  | possible_keys                | key                           | key_len | rows | Extra
posts | range | idx_posts_status_published_at | idx_posts_status_published_at | 86      | 312  | Using where

What changed, and why:

  • type moved from ALL to range — a bounded scan over index entries rather than the whole table.
  • key_len = 86 tells you which part of the index is in play: 81 bytes for status (20 × 4 bytes for utf8mb4 plus a 1-byte length prefix, since the values need no more than 255 bytes) plus 5 bytes for the datetime column. Your numbers will differ with your column types and nullability — the point is that the length shows both columns of the composite index are in use.
  • rows dropped from an estimate of tens of thousands to a few hundred. It is an estimate, not a measurement.
  • Using filesort disappeared: the index already delivers rows in published_at DESC order for a fixed status.

If you want actual execution statistics rather than estimates, MySQL 8.0.18 and later provide EXPLAIN ANALYZE, which runs the statement and reports real timings and row counts. The reference for all plan columns lives in MySQL's EXPLAIN documentation. You can run the same statement from PHP through PDO as you would any other query — see the PDO manual on php.net — which makes it easy to keep plan checks next to the data-access layer where your queries are built.

Composite indexes and column order

A composite index covers several columns, and their order inside the index is not cosmetic. A B+tree on (a, b) is sorted by a first and only then by b — which is why the classic rule holds: an index on (a, b) can serve queries on a alone and on a together with b, but never on b alone. This is the leftmost-prefix rule.

Query patternIndex on (status, published_at) usable?Why
WHERE status = 'published'YesLeftmost column matches.
WHERE status = 'published' AND published_at >= '2026-09-01'YesEquality column first, range column second — the ideal arrangement.
WHERE status = 'draft' ORDER BY published_atYesRows arrive pre-sorted, so no filesort.
WHERE published_at >= '2026-09-01'NoThe leading column is missing; the tree is not sorted by published_at globally.
WHERE status = 'published' AND YEAR(published_at) = 2026NoA function on the indexed column hides its values from the index. Index the column, or define an expression index, or compute a generated column.
WHERE status LIKE '%pub%'No (not this index)A leading wildcard defeats a prefix search.

Ordering rules that work in practice

  1. Equality predicates first (=, IN, IS NULL). These pin the index down to a fixed value and leave the remaining columns sorted.
  2. Range predicates next (>, BETWEEN, LIKE 'x%'). Once a range column is used, columns to its right generally cannot narrow the search further — they can still be filtered after the lookup (index condition pushdown), but they do not skip entries.
  3. Then the columns used for ORDER BY, GROUP BY or DISTINCT, so the engine inherits the sort order and avoids filesorts and temporary tables.
  4. Consider covering last. If adding one more column turns the plan into Using index, the extra column may be worth its write cost.

MySQL 8.0.13 and later can occasionally use an index even when the leftmost column is missing (index skip scan), and EXPLAIN will show it when it happens. Do not design around it — treat it as a bonus, not a plan.

Which columns to index first

When you are staring at a table with fifty columns and no secondary indexes, start from the query, not the schema:

Index the WHERE clause first, then JOIN and ORDER BY columns.
  • Get the actual queries — the slow query log or your APM tool beats guessing.
  • Look at the predicates: those columns are your equality-then-range candidates.
  • Look at join keys: the inner side of a nested-loop join needs an index to avoid a rescan per outer row.
  • Look at sort and group columns: they save filesorts and temporary tables.
  • Check cardinality: a column with a handful of distinct values rarely helps alone, but is often excellent as the leading equality column of a composite index.

For the analytics side — cohort retention queries and similar reporting SQL — this usually means an index on the event timestamp plus the entity id, so each cohort slice is a bounded range scan rather than a table-wide aggregation. Likewise, per-entity aggregate features are often built by queries that touch the same two or three columns over and over.

When an index will not help

  • Tiny tables. The planner knows a full scan is cheap when the table fits in a page or two, and will ignore the index anyway.
  • Low-cardinality columns on their own. A boolean or a status column with three values matches too much of the table; combine it with another column instead.
  • Queries that return a large share of the table. If a filter keeps 60% of rows, scanning may genuinely be the faster plan — an index adds random I/O without removing much work.
  • Functions on the indexed column. WHERE DATE(created_at) = '2026-10-01' hides created_at from the index.
  • Implicit type conversion. Comparing a VARCHAR column to a number makes MySQL convert the column values, so the index is bypassed. Keep predicate types aligned with column types.
  • Leading-wildcard search. LIKE '%term' cannot use a B-tree prefix; that is a job for a full-text index.
  • The wrong columns, however correct the theory. If EXPLAIN still shows type = ALL and your key, the index does not match the predicate — re-read the leftmost-prefix rule before reaching for anything exotic.

When indexes hurt: the write cost

Every index is a second structure the engine must keep in sync. The costs are real and show up on the write path:

  • Slower inserts: each new row must be placed in the correct position of every affected index leaf, not just appended.
  • Slower updates: an UPDATE that changes an indexed column forces index maintenance (and, if the row moves, an insert-and-delete in the clustered index).
  • Slower deletes and more purge work behind the transaction machinery.
  • Disk and memory: indexes consume storage and compete for buffer-pool space that could hold hot data pages.
  • Planner overhead: with many overlapping indexes the optimizer has more choices to evaluate, and occasionally picks a worse one.

The honest trade-off: a read-heavy table with a stable schema loves indexes; a write-heavy table with a dozen rarely-used ones does not. Measure both sides — compare the plan and the insert throughput after the change rather than assuming the index is free.

Common indexing mistakes

  1. Indexing every column individually. A pile of single-column indexes is usually worse than a few composites that match real queries.
  2. Putting the range column first. (published_at, status) cannot serve WHERE status = ? AND published_at >= ? efficiently; swap them.
  3. Duplicating a prefix. If you have (status, published_at), a separate (status) index is almost always redundant.
  4. Indexing by folklore instead of by query. Design from the statements you actually run.
  5. Never deleting dead indexes. Every environment accumulates unused ones; MySQL's sys schema exposes views such as schema_unused_indexes to find them.
  6. Forgetting join columns. A join key that is not part of a constraint does not get an automatic index.
  7. Skipping the verification step. No before-and-after plan means no evidence that anything improved.

A workflow you can repeat

  1. Capture the real statement, including its parameters, from the slow query log or APM.
  2. Run EXPLAIN and note type, key, rows and Extra.
  3. Name the index predictably: idx_<table>_<col1>_<col2>.
  4. Create it on a staging copy or during a maintenance window with CREATE INDEX (in MySQL 8, online DDL keeps the table readable during most index builds).
  5. Run EXPLAIN again. Expect type to move off ALL, key to be non-NULL, rows to drop, and Using filesort to disappear when sorting was the problem.
  6. Check the write side: is this table under heavy insert load? Watch write latency after deployment.
  7. Revisit in a few weeks: unused indexes should be candidates for removal, redundant prefixes for consolidation.

Key takeaways

  • An index converts a full scan into a targeted lookup by giving the engine a sorted structure to walk.
  • B+tree lookups stay shallow: balanced depth, high fan-out, and linked leaves make range scans cheap.
  • Composite column order is a rule, not a preference: equality first, then range, then sort/group columns.
  • Leftmost prefix decides everything — (a, b) serves a and a + b, never b alone.
  • EXPLAIN is the arbiter: check the plan before and after, and use EXPLAIN ANALYZE on MySQL 8 for actual figures.
  • Indexes are not free — they tax every write, consume disk, and can mislead the optimizer if overproduced.
  • Small tables, low-cardinality columns, wildcard searches and functions on indexed columns are the classic cases where an index buys nothing.

Start with one query tonight: pull the slowest statement your application runs, run EXPLAIN, add the smallest index that matches its predicate order, and compare the two plans side by side. That single before-and-after pair will teach you more about indexing than any table of rules — and once you can read the plan confidently, the rest of this guide turns from theory into routine.
