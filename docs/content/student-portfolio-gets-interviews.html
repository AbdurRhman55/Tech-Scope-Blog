Your GPA opens doors narrowly. A transcript says you passed courses; it does not say you can take an ambiguous problem, build something that works, and ship it. A portfolio does — it answers a recruiter's only real question, "can this person ship?", in the seconds before the interview slot is given to someone else.

This is a full guide to building that portfolio: what to include (and what to cut), how recruiters actually scan your work, the anatomy of a project page that gets read, the write-up that makes you memorable, repository details people really check, and a worked example you can copy the shape of. Nothing here promises interviews — no honest article can — but every item below removes a reason for a reviewer to close the tab.

What a portfolio is actually for

A portfolio is not a gallery. It is an evidence file for a hiring claim. Every role you apply for comes with an implicit doubt — "can they handle real code, real users, real trade-offs?" — and your job is to pre-answer it with artifacts instead of adjectives.

Think about how the work is actually consumed. A reviewer at a hiring company gives each candidate an initial pass measured in seconds. In that pass they are not reading your code; they are scanning for signals:

  • Is there a live demo I can open without installing anything?
  • Is there source code I can skim in one click?
  • Do I understand in one sentence what the thing does and for whom?
  • Does the project look finished — or abandoned halfway?
  • Is there any sign a human with judgement built this, not just a tutorial followed?

Design every page of your portfolio against those five questions, in that order. Everything else — the animated header, the personal philosophy page, the blog — is secondary.

Three projects beat ten

Depth signals skill; breadth of half-finished repos signals browsing. A single deployed project with tests, a real README and honest users outweighs a GitHub profile full of tutorial clones and abandoned starts. Recruiters do not count projects — they look for the best one, then check whether the others are noise.

Aim for three projects, each covering a different kind of doubt:

  • One that proves you can build something complete. Deployed, with a database, authentication or whatever "done" means in your stack. This is your flagship.
  • One that proves you can work on real code. An open-source contribution, a maintained team project, or a codebase you inherited and improved. It shows you can read someone else's code and follow a process — see Git workflows that scale past five developers for the habits that make this visible in your history.
  • One that proves taste or range. Something outside the course syllabus: a hardware hack, a data visualisation, a tool you built for your own workflow. It starts conversations interviews cannot.

If you only have one good project, ship one good project. A portfolio of three weak items is worse than a portfolio of one strong one, because the reviewer's only sample is weak.

Anatomy of a strong project page

One page per project, one screen per answer. The structure that works is boring on purpose — familiarity lets the content speak:

  • Title + one-line pitch. "A scheduling tool that turns a shared calendar into bookable slots for university clubs." Noun, verb, user.
  • Two buttons, above the fold: Live demo and Source. Never buried in a paragraph.
  • The problem. Two or three sentences: who hurts, how much, why existing options fail them.
  • Your role and the stack. If it was a team project, say exactly what you built. Then the technologies, one line.
  • A screenshot or two. The product itself, not stock imagery. Alt text that describes what is shown.
  • How it works. Four to six bullets on the interesting decisions — data model, key algorithm, the third-party service you rejected and why.
  • Result and status. Honest: deployed since when, how many users if you can say, what is missing, what you would do next.
  • Trade-offs. The section almost nobody writes, and the one that reads as senior.

Show the reasoning, not just the result

Anyone can follow a tutorial to a finished app. What is rare — and what interviewers remember — is written engineering reflection: the trade-off you weighed, the mistake you made, what you would change with another month. Honest reflection signals seniority faster than a long feature list, because it proves you were paying attention while building.

Write it in the page's "How it works" and "Trade-offs" sections, in plain language, in the past tense:

  • "I used server-side sessions instead of tokens because the app is single-domain and I did not want to manage refresh expiry. If it grew to mobile clients, I would revisit that."
  • "The first version stored derived totals; recomputing them on read removed a whole class of sync bugs at the cost of a slightly heavier query."
  • "I added a test suite after a pagination bug reached users; the suite now covers exactly the four endpoints that ever broke."
  • "The biggest mistake was starting the UI before settling the data model — two rewrites followed."

Keep the register factual, not confessional. You are demonstrating judgement, not performing failure.

Repository hygiene: what reviewers actually open

After the page, the second click goes to your code. Five minutes of reviewer patience is the budget. What they check, roughly in order:

  • README quality. What it is, how to run it in three commands, screenshot, and a short architecture paragraph. A README is a writing sample.
  • Commit history. Readable messages ("fix cart total rounding") beat fifty commits named "update" and one named "final final". History is your process artifact.
  • One clean structure. Monorepo or separate repos — both fine; a repo that mixes five experiments is not.
  • Secrets. No API keys in history, no .env committed. This alone can end a candidacy for security-relevant roles.
  • Dependency and licence basics. A lockfile, a pinned toolchain, and a LICENSE file so anyone can legally read it.
  • Tests where they matter. Not 100% coverage theatre — a handful of meaningful tests on the logic that breaks expensively. Patterns like the ones in clean code patterns for PHP show well here if that is your stack.

Make it findable

The original advice stands, compressed into a checklist you can verify in ten minutes on your phone:

  • Clean domain, fast load, mobile friendly — a portfolio that breaks on a phone loses the reviewer who opens it on the train.
  • Links to live demo and source code up front, on every project page, never behind a contact form.
  • One page per project: problem, approach, result.
  • Your name, email and GitHub/LinkedIn in the footer of every page — do not make a recruiter hunt for how to reach you.
  • A short "About" that states what you are looking for ("backend roles from June, open to internships") in two sentences.
  • Working mailto:, no autoplay audio, no cookie-wall, no popup newsletter modal. Friction is disqualifying at this stage.

Common mistakes

  • Tutorial graveyards. Ten repos that all follow the same course, renamed. If two projects solve the same problem, merge or delete.
  • Dead links. A demo that 404s is worse than no demo — it reads as abandonment. Check all links before every application round.
  • Readme-as-install-script. No context, no screenshots, no "why". Reviewers bounce.
  • Undisclosed team work. Claiming a group project as solo collapses at the first follow-up question. Attribute honestly, describe your part precisely.
  • Overbuilding the wrapper. Weeks on a logo and a WebGL landing page, days on the actual product. Priorities are visible to reviewers.
  • Only-school projects. Zero assigned projects is a gap, but zero self-directed ones is a larger gap.
  • Perfectionism. An honest v1 shipped beats a perfect v2 that exists only in your head. Deploy, then iterate in public — the commit history becomes evidence of exactly that.

Honest limits: what a portfolio cannot do

Be clear-eyed about scope, or the advice stops being useful:

  • Portfolios carry different weight by field. Backend, frontend and infrastructure work translates well to demos; some regulated or embedded roles cannot be shown publicly at all — in that case, describe the problem class and your contribution without leaking the employer's details.
  • Some hiring processes never look. Large companies route graduates through online assessments first; the portfolio matters at the interview stage and in smaller teams. It is a strong second-stage artifact, not a substitute for applications.
  • No artifact guarantees an outcome. What a good portfolio removes are the reasons to say no — a different and more controllable goal.
  • It ages. A project last touched three years ago should either be refreshed or honestly labelled as older work.

One more limit worth stating: a portfolio built only for recruiters dies quickly. The projects that survive review are usually the ones you would have built anyway, just finished and documented properly.

Key takeaways

  • A portfolio is an evidence file for the claim "I can ship" — design it for a scan that lasts seconds.
  • Three deep, finished, deployed projects beat ten tutorial clones; your best project is the only one many reviewers will open.
  • Each project page answers one doubt per block: pitch, demo and source, problem, role, how it works, trade-offs.
  • Write the reasoning — trade-offs, mistakes, what you would change. It reads as senior and it is rare.
  • Repository hygiene is part of the portfolio: README, readable commits, no secrets, tests where they matter.
  • Findability is not vanity: fast, mobile, links up front, reachable by email.
  • Check every link before every application round, and label team work honestly.

Your next step is smaller than "build a portfolio". Pick the strongest thing you have already built, deploy it today on whatever cheap hosting you can get, and write a README with a one-line pitch, three run commands and a screenshot. Then give it the project-page treatment above.
