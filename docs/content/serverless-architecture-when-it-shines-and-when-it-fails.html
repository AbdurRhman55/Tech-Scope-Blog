Serverless promises zero ops. But every architecture has a bill — and the bill is rarely only money. This is a decision guide for developers and architects facing one honest question: does serverless help this particular service, or does it just move the complexity somewhere I can no longer see it?

The direct answer: serverless is a strong default for spiky, event-driven, short-lived and stateless workloads owned by a small team — and a weak one for sustained heavy compute, long-lived connections, costs that must stay predictable at high constant volume, and anything that needs tight control of the runtime. Everything below explains each half of that sentence and hands you a checklist to apply it to your own service.

What serverless actually is

Serverless does not mean "no servers". It means a delivery model: the provider runs the machines, and you deploy units of code — usually functions — that the platform invokes in response to events. You stop provisioning capacity; the provider starts and stops execution environments as work arrives, and meters what actually ran.

Three ideas carry most of the definition:

  • Event-driven invocation. Something causes your code to run: an HTTP request, a queue message, a schedule, a file upload, a database change. Nothing runs until something causes it to.
  • Scale to zero, and back up. When events stop, execution environments are reclaimed. An idle service accrues no compute cost, which is exactly why serverless is so attractive for irregular traffic.
  • A shift in responsibility, not its removal. The provider owns the hardware, patching, and the supervisor that boots your code. You still own correctness, configuration, permissions, data shape, latency budget, and the bill.

Most real "serverless" stacks are two layers: a function layer (your code, run per event) and a set of managed companions — databases, queues, object storage, schedulers, API gateways — consumed per use. The companion layer is where much of the real architecture, and much of the lock-in, lives.

Where it shines

  • Spiky, bursty traffic. Workloads that peak hard and briefly (webhooks, launch-day APIs, batch uploads) pay for what runs and nothing while idle; an always-on deployment pays full price through the troughs.
  • Backends with unpredictable traffic. You stop guessing capacity — the platform absorbs the surprise for you, in both directions.
  • Glue between services. Event routing, cron-style tasks, fan-out jobs and thin API fronts are a few lines of code with no server to patch, no OS to update, no load balancer to tune.
  • Scheduled and background work. Nightly transforms, cleanup jobs, digest emails and report generation run for seconds at a time — the ideal shape for per-invocation billing.
  • Prototypes, internal tools, and staging environments. A service that scales to zero costs nothing while unused, so you can afford to keep many small things alive.
  • Small teams with more product work than ops capacity. Patching, capacity planning and hardware lifecycle are handled by the platform.
  • Per-event isolation. Each invocation is a fresh, bounded unit: one bad request cannot slowly corrupt a long-running process, and failures are scoped to an event rather than a server.
  • Deployment without capacity planning. You push code; the platform decides how many environments to run.

Where it fails

  • Long-lived connections and streaming. WebSockets, long polling and live streams fight the invoke-and-return model. You end up paying for keep-alives or bolting on a separate realtime service anyway.
  • Sustained heavy compute. Once CPU runs continuously, per-request pricing can pass the flat cost of an always-on instance. At constant high utilization, measure before assuming serverless is cheaper.
  • Endpoints that cannot tolerate a cold start. Interactive APIs where the first request after an idle period must feel instant are a poor fit unless you reserve warm capacity — which is a return to always-on economics by another name.
  • Stateful workloads and data locality. Databases, caches and file systems live outside the function. Connection pooling, network placement and throughput become your problem again, and every cold environment must re-establish its connections.
  • Chatty architectures. Splitting one user action into many tiny functions multiplies invocations, network hops and latency — fine-grained serverless microservices can cost more and debug worse than one well-structured service.
  • Deep runtime control. Custom kernels, unusual operating-system tuning, special networking, long-running processes and hardware accelerators are outside what a function sandbox offers.
  • Provider-shaped complexity. Queues, triggers and permission policies are provider-specific. Migrating later is a partial rewrite of the glue, not a configuration change.

What happens on one request

Each hop in a request's path is where latency, cost and failure can enter. An event arrives at a gateway or trigger, the platform finds or creates an execution environment for your function, your handler runs and calls one or more managed services, and a response returns the way it came.

Two properties matter here: the function and the managed service are separate systems over a network — unlike a function calling a library in-process; and the environment in the middle may have been created moments ago for this very request, the subject of the next section.

Cold starts: where the latency comes from

A cold start is the work the platform does when it needs an execution environment and none is warm: it allocates the sandbox, fetches your code and dependencies, starts the runtime, runs your initialization — and the request that triggered it all waits.

  • When it happens: after an idle period, after a deployment, and during a sudden burst that requires more environments than are already warm.
  • What influences it: the size of your package, how many dependencies it pulls in, runtime startup behaviour, and any network configuration your function must join before the handler can run.
  • Who feels it: typically the first request into an idle service — often the first real user of the day.
  • Why it compounds: if the handler opens connections and warms caches every invocation, a cold environment does that work before any useful work happens.

The usual mitigation levers, in rough order of what they cost you:

  1. Trim the package. Fewer dependencies and a smaller artifact mean less to load before your code runs.
  2. Move reusable setup into initialization. Build clients, connections and caches once per environment and reuse them across invocations, instead of re-doing setup inside every handler.
  3. Warm traffic deliberately. A periodic ping keeps environments alive — but you are now paying for idle compute you told yourself you were avoiding, and it papers over the problem rather than solving it.
  4. Reserve warm capacity. Most providers offer provisioned or persistent environments: you exchange some scale-to-zero savings for predictable latency.
  5. Test with production-like dependencies. A function exercised without its network configuration, SDKs and database setup tells you nothing about the cold start your users will meet.

How the cost actually works

No price list belongs in a durable decision guide — prices move, and this article would rot. What does not move is the shape of the billing model — and that shape determines whether serverless is cheap or expensive for you.

  • Two-part metering. Functions are typically billed by a small per-invocation charge plus execution time, often scaled by the memory you allocate. More memory costs more per millisecond but can finish sooner — so the fastest configuration is not automatically the priciest, and the cheapest per-millisecond one is not automatically the cheapest overall.
  • Companions bill per use too. Gateways meter API calls, queues meter messages, storage metered by the gigabyte, and data transfer out is charged. These small units behave like rent: invisible at prototype volume, structural at scale.
  • Idle is free, busy is linear. The model rewards irregular workloads and punishes constant ones. Your job is to figure out which of those you have.
  • Retries multiply the meter. Event sources usually deliver at least once, so duplicate invocations are normal — each one bills, and each one must be safe to run twice.
  • Observability has a meter as well. Traces and logs shipped to managed monitoring services are themselves per-event products; rich instrumentation on a high-volume function is a real line item.
  • Portability is a cost too. Not on this month's invoice, but it appears when you try to leave: engineer time spent unwinding provider-specific glue.

Practical move: build a tiny model in a spreadsheet with your numbers — invocations per day, a rough execution-time distribution, the companion services each request touches, data transfer — and compare it against an always-on deployment at your realistic utilization. No numbers means you are choosing on vibes, not evidence.

Three scenarios, decided

All three scenarios below are invented illustrations of the decision logic — not case studies, not measurements, not real companies.

Scenario A — webhook receiver for a payment provider

  • Shape: bursts of short POST requests, stateless processing, no long-lived connections, near-zero traffic between bursts.
  • Verdict: serverless is close to ideal. Scale-to-zero covers the troughs, each event is handled in isolation, and there is no fleet to patch for something that runs seconds at a time.
  • Watch-outs: event sources retry, so your handler must be idempotent; and the payload still needs signature validation before you trust it.

Scenario B — realtime collaboration sync engine

  • Shape: persistent WebSocket sessions, rooms of connected editors, sub-second fan-out, sessions alive for hours.
  • Verdict: serverless fights you at every step. You would pay to keep connections alive, fight the execution-time ceiling, and split shared in-memory state across environments the platform can reclaim at will.
  • Watch-out: bolting a "realtime" managed service onto the side solves the connection problem but concedes this workload never belonged in functions.

Scenario C — image-tagging API with steady all-day traffic

  • Shape: constant, predictable volume, each request doing meaningful compute for a sustained period.
  • Verdict: undecided until you model it. Idle discounts do not help a service that is never idle, so the per-request meter runs continuously; compare against always-on capacity — or against running inference on hardware you own, the rent-versus-own trade-off we walk through in running models on your own hardware.
  • Watch-outs: model companion services and data transfer too — "steady" traffic is exactly the pattern an always-on deployment is best at.

A migration checklist you can run

  1. Map the traffic shape. Bursty or constant? Idle overnight? Pull real numbers; if you must estimate, label the estimate as one.
  2. Classify the work. Stateless, seconds-long, event-triggered — or stateful, long-running, connection-heavy? The second column mostly disqualifies itself.
  3. Inventory state and data locality. Databases, caches, file-system assumptions, and who owns connection pooling once environments come and go. Stateful services still need their own performance work — start with a practical guide to SQL indexing.
  4. Model cost at your real traffic for both options — gateway calls, queue messages, storage, transfer, monitoring. A demo-tier calculator is not analysis.
  5. Prototype with production-like dependencies — network configuration, SDKs, real database endpoints — and observe what first requests experience before you commit.
  6. Define idempotency and retry semantics. Decide what a duplicate delivery does to your data, and make the answer "nothing" wherever possible.
  7. Set timeouts, quotas and concurrency expectations. Platform quotas become the new capacity limits you report to the business.
  8. Wire observability before launch. Traces across gateway → function → managed services, correlation IDs in logs, alerts per function. Serverless hides the machine; telemetry is your only window.
  9. Draw your portability line. Decide which provider-specific glue you accept and which parts stay portable — and write it down, so the decision survives staff changes.
  10. Move one path first. Migrate a single event flow end to end, keep the old path until the new one is demonstrably at parity, and know your rollback before you need it.

Common mistakes and honest limitations

  • Wrapping a monolith in a function. Moving the same tightly coupled code into a function changes the billing meter, not the architecture.
  • Splitting too finely. One function per step turns a user action into a distributed transaction with a bill attached to every hop.
  • Assuming serverless is cheaper. It runs on a different meter — sometimes dramatically in your favour, sometimes not.
  • Testing in a console with no dependencies. The demo handler is not your handler: no network configuration, no database, no SDK initialization.
  • Skipping observability. Distributed flows across managed services are impossible to debug from log statements alone.
  • Treating provider glue as portable. It is not, and pretending otherwise just delays the reckoning.
  • Ignoring the local development story. Emulators and local runtimes approximate the cloud; the gap is where many teams lose hours.

And the limitations no checklist removes: execution ceilings mean functions are the wrong shape for hour-long jobs (use a batch or job service); quotas are set by someone else; debugging crosses more systems than a monolith did; and the products you depend on evolve on the provider's schedule, not yours. As of October 2026, providers keep adding limits and regional variations — treat any specific number as needing a fresh check against current docs.

Key takeaways

  • Serverless is a metering and operations model, not a magic elimination of infrastructure — someone runs the machines; you run the code and the bill.
  • It shines on spiky, event-driven, short-lived, stateless work — the shape where scale-to-zero and per-event billing work for you.
  • It fails on sustained compute, long-lived connections, tight state, and workloads needing deep runtime control.
  • Cold starts are a real, mitigable cost: trim packages, initialize once per environment, reserve warm capacity if latency demands it.
  • Cost is a mechanism problem — invocations, duration, companions, retries, transfer — not a pricing-page problem. Model it with your own traffic.
  • Migration is a checklist, not a leap: traffic shape → state inventory → cost model → production-like prototype → observability → one path first.
  • Lock-in is a legitimate, explicit trade — accept it on purpose rather than discovering it during an exit.

Your next step: pick one candidate service and run it through the ten-item checklist, writing down the two answers you are least sure about — those are the ones to prototype. Give the prototype a couple of weeks of representative traffic and compare its meter against an always-on deployment at your real utilization. If you keep it, make observability the next investment: serverless takes the machine away from you, and alerts, traces and correlation IDs are how you get it back.
