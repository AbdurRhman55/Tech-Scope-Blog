Git does not get harder with a bigger team — long-lived branches do. The fix is shortening how long work stays unmerged, and choosing the branching model that makes short branches the path of least resistance.

The direct answer: for most product teams, trunk-based development is the default that scales — small commits and pull requests into main, feature flags for unfinished work, branches that live hours rather than weeks, and releases tagged from CI. Reach for git-flow — develop, release/* and hotfix/* branches — only when you ship versioned software on a schedule and must patch several versions in the field at once. The comparison table below shows the criteria; the sections after it show the commands and the migration path.

The real variable is branch lifetime

Team size is a distraction. A team of twenty with branches that live half a day merges more easily than a team of three with branches that live three weeks, because merge pain grows with the amount of divergent history between two integration points — and divergence grows with time, not headcount.

  • Every hour your branch is open, main moves: teammates merge, the schema changes, a shared function changes signature.
  • Conflicts are not caused by Git; they are caused by two people editing the same region before either integrates. Time open is the exposure window.
  • Long branches also hide broken builds, failed integration and half-finished design — you discover them on the day you planned to ship.
  • Short branches make reviews small, and small reviews catch problems while the author still remembers the context.
  • Feature flags decouple deployment from release: code can be merged safely before the feature is ready.

The two models, defined

Trunk-based development

Everyone integrates into a single long-lived branch (main) continuously. Work happens either directly as small commits or on branches that are merged within a day or so. Incomplete work is hidden behind feature flags rather than behind branch age.

  • Branch lifetime: hours to about a day — never "until the feature is done".
  • Integration: continuous; every merge is expected to keep main releasable.
  • Releases: cut from main, ideally by CI on a tag or on merge.
  • Requirement: automated tests and CI on every change, plus tolerance for flags.

Git-flow

A structured model with five branch types: main (production), develop (integration for the next version), feature/*, release/* (stabilize an upcoming version) and hotfix/* (urgent production fixes).

  • Branch lifetime: features live days to weeks; a release branch lives until ship day.
  • Integration: batched at release boundaries; develop accumulates completed features.
  • Releases: a named release/x.y branch is frozen, stabilized, then merged to main and tagged.
  • Requirement: discipline about merging release branches back into develop so fixes are not lost.

Read the table as trade-offs, not ranking. Git-flow is not "old-fashioned" — it encodes a real requirement (several versions supported simultaneously) that trunk-based handles badly. Trunk-based is not "careless" — it demands automation that git-flow lets you postpone.

Trunk-based in practice: the commands

A day of trunk-based work, through one concrete example: adding a cohort filter to a retention view.

# start from a fresh main
git switch main
git pull --ff-only

# short-lived branch
git switch -c feat/cohort-filter

# ... edit, then commit tracked files you changed ...
git commit -am "feat: add cohort filter to retention view"

# pick up teammates' work before you push
git fetch origin
git rebase origin/main

git push -u origin feat/cohort-filter
# open a small pull request; merge after review and green CI
  • git commit -am stages tracked, modified files only. New files still need git add — this is the classic way a file goes missing from a commit.
  • Rebase your own branch onto main before review so the diff reviewers read is exactly your change.
  • If the branch has already been reviewed and others have commented, prefer merging over rebasing — rebasing rewrites commits that reviewers may be pinned to.
  • Keep the branch under a day: if the work is bigger, merge a minimal slice and hide it with a flag.
  • Optional cleanup before review: git rebase -i HEAD~3 to squash fixups into a coherent history — only on commits nobody else has pulled.

Git-flow in practice: the commands

The same work under git-flow, including the release and hotfix paths that exist to serve versioned products:

# feature work integrates into develop, not main
git switch develop
git pull --ff-only
git switch -c feature/invoice-export
# ... commits ...
git pull --rebase origin develop
git push -u origin feature/invoice-export
# then: merge with --no-ff so the feature stays visible in history
git switch develop
git merge --no-ff feature/invoice-export
git branch -d feature/invoice-export

# cut a release: scope is frozen, only fixes are accepted
git switch -c release/1.4 develop
# ... version bump, release notes, fixes only ...
git switch main
git merge --no-ff release/1.4
git tag -a v1.4.0 -m "v1.4.0"
git switch develop
git merge --no-ff release/1.4
git branch -d release/1.4

# urgent production fix against the version in the field
git switch -c hotfix/1.4.1 main
# ... fix ...
# merge back to main (tag v1.4.1) AND to develop, or the fix reappears
  • The merge-back rule is the whole model. Every release/* and hotfix/* branch merges into both main and develop; skip that and the next release silently loses the fix.
  • Use --no-ff on integration merges so feature and release boundaries remain visible in the log.
  • If your team never patches an older version, the develop and release/* branches are ceremony — you are paying git-flow's overhead without using its one real benefit.
  • The git flow command-line helper automates these steps, but plain Git commands show exactly what the model does.

For the mechanics of day-to-day Git itself — remotes, recovery, inspection — the official Git documentation is the reference this article assumes.

How to decide: fit statements

Choose trunk-based if:

  • Your team deploys to production routinely — several times a week or more — and can roll back.
  • CI runs tests on every push and a green main is a team norm.
  • You are happy to ship disabled code behind flags and delete the flag when the feature lands.
  • There is exactly one version in production at any moment.
  • You want onboarding to be "here is how we merge", not "here is a diagram of five branch types".

Choose git-flow if:

  • You release versioned artifacts on a cadence — app-store approval cycles, dated product editions, packaged installs.
  • Customers run older versions in the field and you must ship fixes to more than one of them.
  • QA, legal or marketing gates a release, so a freeze period with a stabilizing branch is genuinely useful.
  • Releases are events that need a named branch, notes and a tag — not just "whatever is on main today".

Many teams land in a hybrid: trunk-based development with a release branch cut from main for a few days when a release needs stabilization. That keeps branch lifetime short without pretending every merge is shippable.

Rules that prevent pain

  1. Rebase your own branch freely; never rewrite shared history. Anything another developer may have pulled (main, develop, a reviewed branch) gets git revert, not a force-push.
  2. Force-push only with a lease, only on your own branch: git push --force-with-lease refuses to overwrite commits you have not seen — plain --force can destroy a teammate's work.
  3. Protect main in the forge. No direct pushes; every change arrives through a reviewed pull request with green CI.
  4. Require pull-request reviews but keep them small. A diff someone can read in a few minutes gets real attention; a 2,000-line diff gets a thumbs-up.
  5. Tag releases from CI — never from a laptop. A laptop tag is unreproducible, unreviewed, and depends on a working copy nobody else can see.
  6. Merge or discard stale branches on a schedule. A branch older than your team's stated lifetime target is a decision waiting to be made, not a background object.
  7. Never merge with failing CI. One red merge teaches everyone that red is normal.
  8. Resolve conflicts by understanding both sides. Taking "theirs" wholesale to make the merge go through is how a teammate's change quietly disappears.

Small reviews are also where static checks earn their keep: a reviewer should be reading logic, not hunting for a possibly-undefined value. The TypeScript pitfalls that bite newcomers show what the compiler can catch before a human has to.

Common mistakes at scale

  • The three-week branch. It starts as "just this one big thing". Split the work into mergeable slices and flags instead.
  • Giant pull requests. If reviewers cannot hold the change in their head, defects and design problems both slip through.
  • Rebasing published history. Rewriting a branch a reviewer has commented on invalidates their review and can orphan their comments.
  • Flags that never die. A flag system without a deletion habit becomes a second configuration system nobody understands. Give every flag an owner and a removal condition.
  • Release-branch drift. Hotfixes patched into main but never merged back to develop resurface in the next release — the classic git-flow failure.
  • Manual, tribal release steps. If releasing requires one person's shell history, you do not have a workflow, you have a dependency on an individual.
  • Fighting about rebase vs merge instead of agreeing on the branch lifetime. The lifecycle decision matters more than the plumbing.

Moving an existing team, step by step

  1. Write down your current model honestly — including the exceptions everyone knows about but nobody documented.
  2. Protect main and require CI plus one review. This is the change with the highest ratio of pain removed to effort spent.
  3. Set a branch-lifetime target as a team (for example, a day or two for product work) and make visible branch age part of your stand-up or board.
  4. Split the next large piece of work into a mergeable first slice plus a flag, and run it as the template.
  5. Automate tagging and release notes in CI so shipping stops depending on anyone's laptop.
  6. Retire branches you do not need. Drop develop if you only ever ship one version; add release/* only if you patch versions in the field.
  7. Review after a month: are merges smaller, are conflicts rarer, is releasing boring? Adjust the target, not the philosophy.

Key takeaways

  • Git scales fine; unmerged time does not. Shorten branch lifetime before adopting more process.
  • Trunk-based suits continuously deployed products; git-flow suits versioned releases with parallel support. The criteria table is the decision.
  • Trunk-based requires CI and feature flags; git-flow requires merge-back discipline. Both fail when their one requirement is skipped.
  • Rebase your own work, never shared history; protect main; force-push only with --force-with-lease.
  • Small pull requests and CI-tagged releases are the two habits that remove most release-day risk.
  • Hybrid is legitimate: trunk-based day to day, a short stabilization branch when a release needs one.

When integration is continuous, releases become boring. Boring is the goal.
